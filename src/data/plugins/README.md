# Plugin Docs Automation

## Overview

The VeeCode Platform site at **platform.vee.codes/en/resources/** displays a catalog of Backstage plugins with descriptions, tags, and links to full documentation.

Adding a new plugin to the site requires only one step: **add an entry to `catalog.yaml`**. CI handles the rest -- fetching the README, generating bilingual descriptions (EN + PT-BR) via Claude, and opening a PR with all the generated files.

## Architecture

```
catalog.yaml (source of truth)
     |
     v
prepare job (parse YAML -> matrix JSON)
     |
     v
matrix jobs (N parallel, 1 per plugin)
  each: fetch README -> claude-code-action generates EN + PT-BR descriptions -> artifact
     |
     v
merge job (collect artifacts -> generate plugins.json + patch locales -> open PR)
```

The workflow lives in `.github/workflows/sync-plugins.yml` and runs:
- **Weekly** on Monday at 6:00 AM UTC (cron)
- **On demand** via `workflow_dispatch`

## Files

| File | Purpose |
|------|---------|
| `src/data/plugins/catalog.yaml` | Source of truth. All plugins listed here with metadata. |
| `src/data/plugins/plugins.json` | Auto-generated by CI. Consumed by the Next.js site at build time. |
| `src/data/plugins/readmes/` | Pre-cached READMEs for npm/oci plugins (not GitHub). |
| `locales/en.json` | English descriptions patched by CI (under the `resources` key). |
| `locales/pt.json` | PT-BR descriptions patched by CI (under the `resources` key). |
| `.github/workflows/sync-plugins.yml` | The CI workflow that orchestrates everything. |

## How to Add a New Plugin

1. Edit `src/data/plugins/catalog.yaml`.
2. Add an entry under `plugins:`:

```yaml
- id: my-plugin
  title: "My Plugin"
  path: my-plugin
  visible: true
  source: "github:owner/repo/tree/branch/path"  # or npm:package-name or oci:registry/image
  npm: "@scope/package-name"  # optional, informational
  image: "https://url-to-icon.svg"
  tags: [Tag1, Tag2]
```

3. Set `visible: true` to show the plugin on the site, or `false` to keep it hidden.
4. Commit and push to `develop`.
5. Either wait for the weekly cron (Monday 6 AM UTC) or trigger the workflow manually.
6. CI will open a PR (`chore/sync-plugin-docs`) with updated `plugins.json` and locale files.
7. Review and merge the PR.

### Field Reference

| Field | Required | Description |
|-------|----------|-------------|
| `id` | Yes | Unique identifier. Used as key in locale files and for artifact naming. |
| `title` | Yes | Display name shown on the site. |
| `path` | Yes | URL slug for the plugin detail page (`/plugin/{path}`). |
| `visible` | Yes | `true` to list on the site, `false` to hide. Hidden plugins are skipped by CI. |
| `source` | Yes | Where to fetch the README. See **Source Types** below. |
| `npm` | No | npm package name. Informational only (not used for fetching unless source is `npm:`). |
| `image` | Yes | URL to the plugin icon/logo displayed in the catalog. |
| `tags` | Yes | Array of tags for filtering on the resources page. |

## Source Types

The `source` field determines how the plugin's README is fetched:

- **`github:owner/repo/tree/branch/path`** -- Fetches `README.md` from `raw.githubusercontent.com`. The README is fetched at runtime for detail pages (always fresh) and during CI for description generation.

- **`npm:@scope/package-name`** -- Fetches README from the npm registry API. The README is pre-cached in `src/data/plugins/readmes/{id}.md` because npm content is not available via a simple URL at runtime.

- **`oci:registry/image`** -- Extracts README from an OCI image layer (tar.gz). Also pre-cached in `readmes/` for the same reason as npm.

## How Descriptions Are Generated

1. The CI workflow fetches each plugin's README based on its `source` type.
2. Claude (via `claude-code-action` with `claude-sonnet-4-6`) reads the README and generates:
   - A concise 1-2 sentence description in **English**
   - The same description translated to **Brazilian Portuguese** (PT-BR)
3. Both descriptions are written into `plugins.json` (under `en` and `pt` arrays) and patched into the locale files (`locales/en.json` and `locales/pt.json` under the `resources` key).

No manual translation is needed. If a README is empty or unavailable, the description defaults to "No description available."

## Detail Pages

How the full plugin documentation is displayed depends on the source type:

- **GitHub plugins:** The README is fetched at runtime from `raw.githubusercontent.com` via `convertUrlToRaw()`. This means the detail page always shows the latest version.

- **npm/oci plugins:** The README is pre-cached at `src/data/plugins/readmes/{id}.md` during the CI run and loaded at build time. To update these, re-run the CI workflow.

## Manual Trigger

Trigger the workflow without waiting for the weekly cron:

```bash
gh api -X POST \
  repos/veecode-platform/VeeCode-site/actions/workflows/sync-plugins.yml/dispatches \
  -f ref=develop
```

Or use the GitHub UI: Actions tab > "Sync Plugin Docs" > "Run workflow" > select `develop`.

## Key Design Decisions

- **`catalog.yaml` is curated, not auto-discovered.** This gives explicit control over what appears on the site. Not every published plugin needs to be listed.

- **Claude generates bilingual descriptions from READMEs.** No manual writing or translation required. Descriptions stay consistent in tone and length.

- **`plugins.json` is generated, never hand-edited.** CI is the source of truth for descriptions. Manual edits will be overwritten on the next sync.

- **GitHub READMEs are fetched at runtime (always fresh). npm/oci READMEs are pre-cached (need a CI re-run to update).** This is because GitHub provides predictable raw URLs, while npm/oci content requires API calls or binary extraction that can't happen client-side.

- **Only `visible: true` plugins are processed by CI.** Set `visible: false` to keep a plugin in the catalog for future use without generating docs for it.
